# GPT-SoVITS-v2pro 依赖版本冲突解决记录

**日期**: 2026-07-29
**环境**: AutoDL 容器, NVIDIA RTX 4080, conda base 环境 (`/root/miniconda3`, Python 3.12)
**项目路径**: `/root/autodl-tmp/tts/GPT-SoVITS-v2pro/GPT-SoVITS-v2pro-20250604-nvidia50`
**目标文件**: `webui.py`（启动入口 `app.queue().launch(...)`，约 1975 行）

---

## 一、问题现象

启动 `python webui.py` 后，服务端能起来（`Running on local URL: http://0.0.0.0:9874`），
但浏览器打开页面反复报错，后台日志刷屏：

```
gradio/routes.py:405        → templates.TemplateResponse("index.html", {dict...})
starlette/templating.py:148 → template = self.get_template(name)
jinja2 ... cache.get(cache_key)
TypeError: unhashable type: 'dict'
```

期间还伴随几个衍生问题：
- `OSError: Cannot find empty port in range: 9874-9874` —— 旧进程没退，端口被占用。
- `ValueError: When localhost is not accessible` —— AutoDL 代理环境变量劫持了 localhost 请求。
- `Could not create share link. Missing file: frpc_linux_amd64_v0.2` —— `launch()` 里 `share=True` 想建公网链接但缺 frpc 二进制（非致命）。

---

## 二、根因

gradio 4.38.1 调用 starlette 的 `TemplateResponse` 时使用的是**旧签名**：

```python
# 旧签名（starlette < 0.37）：第一个位置参数是模板名
templates.TemplateResponse("index.html", {"request": request, ...})
```

而 **starlette ≥ 0.37.0** 把签名改成了 `TemplateResponse(request, name, context)`，
第一个位置参数被当成 `request`，于是 gradio 传入的 `"index.html"` 落到了 `request`，
那个 dict 被当成了 `name`（模板名），`get_template(dict)` 触发
`TypeError: unhashable type: 'dict'`。

**本质**：gradio 4.38.1 必须搭配 `starlette < 0.37`（即 0.36.x），而 fastapi 的新版本
强制要求更新版 starlette，于是产生连锁冲突。

---

## 三、版本冲突踩坑记录（核心）

| 组合 | 结果 | 原因 |
|------|------|------|
| `gradio==4.38.1` + `starlette==0.36.3` + `fastapi==0.115.6` | ❌ 安装失败 | fastapi 0.115.6 依赖 `starlette>=0.40.0`，与 `starlette==0.36.3` 冲突，整次安装中止 |
| `gradio==4.38.1` + `starlette==0.36.3` + `fastapi==0.110.1` | ❌ 安装失败 | fastapi 0.110.1 依赖 `starlette>=0.37.2,<0.38.0`，与 `starlette==0.36.3` 冲突 |
| ✅ `gradio==4.38.1` + `starlette==0.36.3` + `fastapi==0.109.2` | ✅ 成功 | fastapi 0.109.2 依赖 `starlette>=0.36.3,<0.37.0`，正好兼容 `starlette==0.36.3` |

**结论**：要让 gradio 4.38.1 正常工作，starlette 必须锁 `0.36.3`，而与之兼容的 fastapi
最高只能到 `0.109.2`（不能是 0.110+）。

---

## 四、最终可用版本组合

| 包 | 锁定版本 | 说明 |
|----|----------|------|
| gradio    | `4.38.1` | WebUI 框架，固定此版本 |
| starlette | `0.36.3` | 必须 < 0.37，匹配 gradio 旧 TemplateResponse 签名 |
| fastapi   | `0.109.2` | 唯一与 starlette 0.36.3 兼容的 fastapi（依赖 `starlette>=0.36.3,<0.37.0`） |
| jinja2    | `3.1.3`  | 模板引擎，固定避免缓存异常 |

---

## 五、解决步骤（可直接复用的命令）

```bash
# 1. 在 base 环境下安装兼容版本组合（注意 fastapi 是 0.109.2，不是 0.110/0.115）
pip install "gradio==4.38.1" "jinja2==3.1.3" "starlette==0.36.3" "fastapi==0.109.2"

# 2. 验证版本确实生效（必须看到下面四行一致）
python -c "import starlette, gradio, jinja2, fastapi; \
print('starlette', starlette.__version__, '| gradio', gradio.__version__, \
'| jinja2', jinja2.__version__, '| fastapi', fastapi.__version__)"
# 预期: starlette 0.36.3 | gradio 4.38.1 | jinja2 3.1.3 | fastapi 0.109.2

# 3. 清除 AutoDL 代理（否则 localhost 不可达）
unset http_proxy https_proxy all_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY
export no_proxy="localhost,127.0.0.1"

# 4. 如端口被旧进程占用，先清掉再启动
pkill -f webui.py
python webui.py
```

---

## 六、其他注意事项

1. **端口占用**：`OSError: Cannot find empty port` 说明上次进程没退，用 `pkill -f webui.py`
   杀掉旧进程，或换 `server_port=9875` 等空闲端口（SSH 隧道也要相应改成 `-L 9875:localhost:9875`）。
2. **share 链接**：AutoDL 上用 SSH 隧道访问即可，不需要公网 share。确认 `webui.py` 的
   `launch()` 里 `share=False`（默认值），可消除 `frpc_linux_amd64_v0.2` 缺失的警告噪音。
   若之前手改过 `webui.py` 出错（如 `shart` 拼写、`share=` 重复参数 SyntaxError），用
   `git checkout -- webui.py` 还原（无 git 跟踪则手动改回原 launch 参数）。
3. **代理是每次新 shell 都要重新 unset** 的，重开终端后需再次执行第 3 步。

## 七、小结

页面打不开的根因是 **starlette 版本过高（≥0.37）与 gradio 4.38.1 的 TemplateResponse
旧签名不兼容**，而 fastapi 0.110/0.115 又强制要求高版本 starlette，形成死锁。
解法锁定为：`gradio==4.38.1` + `starlette==0.36.3` + `fastapi==0.109.2` + `jinja2==3.1.3`，
并配合清代理、清端口、关 share 即可正常启动。

进展到训练阶段了！现在报错是 `OSError: AF_UNIX path too long`——这是 **torch 多进程（DataLoader 的 fork 子进程间共享 CUDA 张量）要建一个 Unix 域套接字，但套接字路径超过了 Linux 的 ~108 字节限制**。

根因：你的项目路径特别长（`/root/autodl-tmp/tts/GPT-SoVITS-v2pro/GPT-SoVITS-v2pro-20250604-nvidia50` 已经 70+ 字符），而 PyTorch 的 `resource_sharer` 把套接字建在 `tempfile.gettempdir()` 下，如果 `TMPDIR` 被设成了某个长路径，拼出来的 socket 路径就超长了。

**修复：把临时目录指到短的 `/tmp` 再启动训练**（必须在启动训练命令之前 export，因为 Python 在进程启动时就会缓存 tempdir）：

```bash
export TMPDIR=/tmp
export TMP=/tmp
export TEMP=/tmp
```

为了保险，再把项目软链到一个短路径，从短路径下启动（避免任何地方用到超长 cwd）：

```bash
ln -sfn /root/autodl-tmp/tts/GPT-SoVITS-v2pro/GPT-SoVITS-v2pro-20250604-nvidia50 /root/p
cd /root/p
```

然后重新跑你的训练启动命令（保持上面的 `TMPDIR=/tmp` 环境变量生效）。

---

如果设置了 `TMPDIR=/tmp` 后还报同样的错，那就是 DataLoader 的 `num_workers` 在 fork 时仍触发了超长路径，可以临时把训练脚本里的 `num_workers` 改成 `0`（牺牲一点数据加载速度，但能绕过多进程共享）。不过先试 `TMPDIR=/tmp` + 短路径软链，大概率直接好。

训练跑通后，推理又卡在 `onnxruntime`：`ImportError: libcudart.so.13`。

**根因**：你环境里的 `onnxruntime` 是个 **CUDA 13 构建版**（G2PW 拼音模型用它来跑 ONNX），它需要 `libcudart.so.13`，但你现在的 CUDA 运行时是 cu124（`libcudart.so.12`，torch/torchaudio 用的那个），所以加载失败。

**最稳的修法**：GPT-SoVITS 的 G2PW 拼音推理在 **CPU 版 onnxruntime** 上完全能跑（它只是轻量的字音转换），而且不依赖任何 CUDA 运行时，彻底避开版本纠缠。把现在的 GPU 版卸掉、装 CPU 版：

```bash
pip uninstall -y onnxruntime onnxruntime-gpu
pip install onnxruntime
```

装完验证（不再报 `libcudart.so.13` 即成功）：

```bash
python -c "import onnxruntime; print('onnxruntime', onnxruntime.__version__)"
```

然后重新启动推理 `inference_webui.py` 即可。
